# Argo CD write-operation contract research

Research date: **November 7, 2026**. Scope: `restart-indexer-worker`, `roll-back-billing-worker`, and `sync-prod-payments-api` only.

This is research and a bounded implementation recommendation, **not qualification evidence from a running Argo CD installation**. Read the three instructions/TOMLs, captured tool surface, connector catalog entry, relevant replica source, and narrowly projected fixture identities, application policies/status/history, resource metadata/workload images/status, revision mappings, and project/cluster permissions. No Secret contents, ConfigMap data, logs, or cluster credential configuration were needed or read. Public-source requests contained no fixture credentials. No accounts, deployments, package installation, tests, benchmark/inference runs, commits, branches, or pushes were used. Only this note is an intended write; Vercel is outside scope.

Evidence labels:

- **[L]** Local instruction, fixture projection, configuration, or replica implementation; not vendor authority.
- **[P]** Exact published MCP package/source pin.
- **[D/U]** Official versioned documentation / upstream implementation at the registered pins.
- **[I]** Inference, objection, or proposed evaluator decision; not an already implemented guarantee.

The scenario clocks are **October 29, 2026**, at 14:05Z for restart/billing and 14:15Z for payments. “This morning,” “an hour ago,” and “today” belong to those simulated clocks, not November 7 wall time. The Lua action uses its execution environment's clock; do not require a November 7 timestamp in the fixture.[^local-restart][^local-billing][^local-payments][^lua]

## 1. Findings that should block an unqualified success claim

1. **Billing can currently pass without deploying the rollback. [L/I]** The fixture's live worker Deployment uses `billing-worker:1.43.0`, has no `targetManifest`, and the old revision record supplies a `Healthy` label but no revision-specific workload. The replica adopts revision health, marks resources synced, and replaces a live manifest only when `targetManifest` exists. Consequently, a revision/status/history-only rollback can leave the worker image and old pod state in place. The instruction says to actually deploy `v1.42.0`; changing status is not equivalent. A bounded revision-to-desired-workload model or explicit nonqualification is necessary.[^local-billing-data][^local-model][^health][^kube-deployment]
2. **The pinned application-update tool cannot preserve existing target labels/finalizers. [P/U/L/I]** Its schema exposes only metadata name/namespace. The billing fixture has `team`/`env` labels and `resources-finalizer.argocd.argoproj.io`; the upstream full update replaces labels, annotations, and finalizers with the submitted values. The reference-shaped update therefore drops them, as does the replica. A new strict preservation rule would make an otherwise intended native solution unreachable. Conversely, silently accepting their loss as harmless vendor metadata would be wrong. This needs an explicit connector/condition decision, not a stealth instruction change.[^mcp-schema][^mcp-client][^server-update][^local-billing-data][^local-apps]
3. **Presence of `automated` is not “automated sync on.” [D/U/L/I]** `automated.enabled:false` disables it, even with `prune:true`/`selfHeal:true`. The existing billing existence assertion and replica object-presence guards miss this. The pinned MCP update schema cannot express `enabled`, so distinguish a vendor state predicate from currently reachable tool inputs.[^auto-doc][^types][^local-billing][^local-model][^mcp-schema]
4. **Request/response-shaped success is insufficient. [P/U/I]** The connector discards HTTP status at its client-method boundary and ordinarily wraps a returned JSON error body with `isError:false`. Sync acceptance is asynchronous upstream, restart returns an empty response after a live patch, and a dry-run prune can report `Pruned` without deleting anything. Require evidence of the authorized durable effect, not an HTTP call, MCP flag, revision string, or success message alone.[^mcp-http][^mcp-client][^mcp-server][^server-sync][^server-action][^engine-sync]
5. **There are version/wire compatibility traps hidden by replica permissiveness. [P/U/L/I]** The connector uses the legacy resource-action endpoint. Argo CD `v3.1.0` and `v3.1.1` omit the action name when forwarding that endpoint to V2; `v3.2.5` copies it. Separately, the connector sends per-operation `syncOptions` as a bare array, while upstream declares a message with an `items` array. The replica accepts the latter mismatch. Neither is evidence that the task is impossible generally, but both prevent using the mock's success as proof of arbitrary upstream-version compatibility.[^legacy-310][^legacy-311][^server-action][^proto][^gateway][^mcp-client][^local-apps]

## 4. Native MCP boundary versus vendor API versus replica

### Reachable tools and exact translation

**[P/L]** All three workflows use a native npm MCP server pointed at the benchmark HTTP world. The captured tools include `list_applications`, `get_application`, `get_application_resource_tree`, `get_application_managed_resources`, `get_resources`, `get_resource_actions`, `update_application`, `sync_application`, and `run_resource_action`. There is **no exposed generic HTTP tool, application patch tool, resource patch/delete tool, rollback-by-history tool, wait tool, or revision-metadata tool**. Native Argo API capabilities do not magically become MCP affordances.[^local-catalog][^local-snapshot][^mcp-server]

| MCP call | Pinned HTTP translation |
| --- | --- |
| `get_application` / resource tree | GET the name-based path, with `appNamespace` query when supplied. Omission selects the server's default namespace, not an arbitrary same-name app.[^mcp-client][^namespace-doc] |
| `get_application_managed_resources` | GET managed-resources with its unusually named **`appNamespace`** tool argument; other tools use `applicationNamespace`. Returned `targetState`/`liveState` are serialized-manifest representations, not mutations.[^local-snapshot][^mcp-client][^server-resource] |
| `update_application` | PUT `/api/v1/applications/{applicationName}` with the supplied Application as the body; namespace comes from **`application.metadata.namespace`**, not an additional tool argument. Its required full simplified spec is not a merge patch.[^mcp-client][^mcp-schema][^proto] |
| `sync_application` | POST `/api/v1/applications/{applicationName}/sync`; supplied application namespace becomes body **`appNamespace`**. It forwards `dryRun`, `prune`, `revision`, and optional `syncOptions`; omitted flags are not invented.[^mcp-client][^proto] |
| `run_resource_action` | POST `/api/v1/applications/{applicationName}/resource/actions`; query contains `appNamespace`, resource `namespace`, `resourceName`, `group`, `kind`, and `version`. Body is a **JSON string**, e.g. `"restart"`, not an Application and not the V2 action-request object.[^mcp-client][^proto] |

**[P/U] UID constraint:** `resourceRef.uid` is required by the MCP schema but is **not forwarded** for action discovery, action execution, or resource reads. The upstream resource/action request protobufs have no UID field. Server membership resolution finds the app's resource-tree node by group/kind/namespace/name and requires that node to have a UID; it then obtains the live resource in the app's destination cluster. Thus a correct UID is useful discovery evidence, but this action route does **not** give the caller an optimistic UID precondition. Do not require a nonexistent UID query/header, claim stale UIDs are rejected, or grade a UID string alone as sufficient targeting. A recreated same-name Deployment creates a real race; a fresh tree/resource read narrows, not eliminates, it.[^mcp-schema][^mcp-client][^proto][^server-resource][^kube-uid]

**[P/I] Read-path caveats:** `list_applications` strips sync policy, operation state, history, and UID, while preserving application name/namespace, source/destination, project, and sync/health summary. It is adequate for disambiguation, not billing policy preservation or proof of a new deployment. An error JSON without `items` can turn into an apparently successful empty list. Also, `get_resources` with omitted/empty refs fetches its tree **without forwarding the application namespace**, then uses the namespace for individual resource reads. Explicit refs or explicitly namespaced tree/managed-resource tools avoid that pinned-client trap for payments.[^mcp-client][^mcp-server]

### Unsupported-success traps

- **[P] HTTP failures can be MCP “successes.”** `HttpClient` parses JSON and returns `{status, headers, body}` without checking `response.ok`; the operation methods usually return only `body`. The outer wrapper reports `isError:false` unless an exception is thrown. A 401/403/409/500 JSON body is therefore not reliable positive evidence. Conversely a non-JSON error can throw after an operation whose result is unknown.[^mcp-http][^mcp-client][^mcp-server]
- **[P/U/L] `syncOptions` shape mismatch:** the MCP/client array is sent as an array; upstream `ApplicationSyncRequest.syncOptions` is a `SyncOptions` message, whose JSON object has `items`. The normal generated gateway decodes into that protobuf before invoking Sync. The replica deliberately accepts both. No live decoding check was run, so classify this as an evidenced wire incompatibility requiring qualification, not a measured error rate. The straightforward native payments/billing paths omit per-call `syncOptions` and inherit app options upstream; no user requirement needs this questionable field.[^mcp-client][^proto][^gateway][^server-sync][^local-apps]
- **[U/P] Legacy-action version issue:** at `v3.1.0`/`v3.1.1`, the legacy adapter constructs V2 without `Action`, so the V2 implementation sees an empty action. The pinned MCP does not expose V2. At the selected `v3.2.5` baseline, `Action` is copied. Do not silently emulate the broken adapter and then call the user request invalid, nor assert the connector works on every server version.[^legacy-310][^legacy-311][^server-action][^mcp-client]
- **[P/U/I] Narrow schema, broad update:** `ApplicationSchema` cannot express existing labels/finalizers, arbitrary annotations, `automated.enabled`/`allowEmpty`, retry `refresh`, multiple sources, Helm/Kustomize source options, or `ignoreDifferences`. Unknown fields are not a supported preservation escape hatch; the captured JSON schema disallows them. A full update may erase fields that this client cannot round-trip. This is particularly material here because labels/finalizers really exist, not just a theoretical future fixture issue.[^mcp-schema][^local-snapshot][^server-update][^local-billing-data]

## 5. Restart: patch intent, rollout, and preservation

**[D/U]** The baseline built-in Deployment restart Lua ensures the pod-template metadata/annotations maps exist, then sets:

`spec.template.metadata.annotations["kubectl.kubernetes.io/restartedAt"]`

to a UTC timestamp with second precision. It returns the object. The server calculates a merge patch against the live object and applies it to Kubernetes; an empty diff causes no patch. This is **not an Application update, Git edit, application sync, pod delete, Deployment delete/recreate, scale action, or pause/resume action**. It does not remove `spec.paused` or set it to false.[^lua][^server-action]

**[D/U/I]** A changed pod template initiates the Deployment controller's rollout when not paused. The controller can create/adopt a matching ReplicaSet and later replace pods; the Deployment UID is retained, while child identities/ReplicaSet revisions/status may legitimately change. A pod's container restart counter is not a necessary rollout signal: replacement pods are new objects. Annotation acceptance is evidence of the requested restart trigger, not synchronous evidence that all replacement pods are ready, have consumed the new secret, or stopped returning 401. Do not inspect or disclose the secret to manufacture stronger proof.[^kube-deployment][^kube-uid][^engine-health][^local-restart]

**[U/I]** Action availability/behavior is configurable through Argo CD resource overrides; custom actions can supersede built-ins. `get_resource_actions` is useful discovery, but is neither a mandatory protocol handshake nor a guarantee that a later action remains permitted. Action execution checks app/resource membership, action RBAC, project/resource permissions, and Kubernetes access. The replica's static action list is not proof of installed Lua or authorization.[^actions-doc][^server-action][^server-resource][^local-resources]

**[L/I] Minimal authorized state contract:**

- Observe a previously absent restart annotation becoming a nonempty valid timestamp on the **production worker pod template**, bound to an authorized restart action in that app/resource/cluster identity. Here absence-to-presence is meaningful because the initial annotation is absent; do not generalize an existence-only check to fixtures that already have one.[^local-restart][^local-restart-data][^lua]
- Preserve Application spec/source/policy and its last deployed sync operation/history; retain unresolved config drift and do not apply its `targetManifest`. Allow action events, resource version/generation updates, and bounded worker-rollout-derived state only. The API Deployment and its descendants, all staging resources, and independent config/data are not restart collateral.[^local-restart][^local-restart-data][^server-action][^kube-deployment]
- Preserve nonpaused semantics. The TOML requires the `paused` key to remain **absent**; absent and false both mean unpaused in Kubernetes, but the built-in action itself does not change this key. Do not invent an extra `resume` mutation merely to normalize representation.[^local-restart][^lua][^kube-deployment]
- Keeping the app `OutOfSync` is task-correct, not a failure. A resource action may affect subsequent resource comparison/status, but must not certify the unreviewed Git change as deployed or append an Argo sync deployment-history entry.[^local-restart][^local-restart-data][^server-action][^controller-sync][^controller-history]

**[I] Bounded support choice:** if the benchmark models only action acceptance/live-template patching, state that limit and do not grade a fictional completed secret-refresh rollout. If it claims full restart completion, represent bounded worker child/observed-generation progress; avoid demanding exact new pod names, UIDs, counts of intermediate events, or instantaneous health.

## 6. Billing: persistent source pin versus one-off sync

### Effective automation

**[D/U]** Evaluate automation with the vendor predicate:

`syncPolicy.automated is a non-null object AND automated.enabled is not false`

Missing/null `automated` is off. An empty object or an object with `enabled` omitted/null is on. `enabled:true` is on. `enabled:false` is off regardless of prune/self-heal settings. `prune`, `selfHeal`, and `allowEmpty` are separate behavioral flags; their presence does not enable automation. The exact client can express its existing `{prune:true,selfHeal:true}` representation, but not all vendor-valid equivalents.[^auto-doc][^types][^mcp-schema]

**[L/I]** “Keep automated sync turned on” should be checked throughout the workflow, not only at the end. Preserve existing prune/self-heal, retry, destination, repository, source path, project, and other independently meaningful configuration. Do not silently strengthen the original instruction into an exact textual policy object requirement; separately identify preservation of preexisting independent fields.[^local-billing][^local-billing-data]

### Persist desired state, then observe deployment

1. **[D/U]** Changing `targetRevision` to the tag changes the application's future comparison/reconciliation source. A tag tracks that Git ref and can be retagged; a SHA is more immutable. The user explicitly requests **the `v1.42.0` Git tag**, so a final SHA, `main`, image-only override, or one-off sync to an old SHA is not a substitute, even though some are valid vendor deployment mechanisms.[^tracking-doc][^local-billing]
2. **[U]** Upstream full `Update` validates and writes the Application and briefly waits for informer visibility, **not rollout completion**. The controller separately compares desired/live resources and starts automated sync when needed. Current `Synced`/`Degraded` state does not forbid rollback: changing the desired revision can make it OutOfSync. Existing historical deployment of the old SHA is not enough to suppress this new source change; duplicate-attempt logic compares the latest operation's source/revision context, not mere existence anywhere in history.[^server-update][^controller-auto][^local-billing-data]
3. **[U]** The server rejects a non-dry-run, single-source manual sync with a nonempty revision string that differs from the configured target when effective automation is on. This check is performed on the requested ref string **before resolving equivalent commits**. After pinning `v1.42.0`, an explicit manual sync using `revision:"v1.42.0"` or omitting revision can be valid; using `revision:"b0826e..."` can still be rejected even though it resolves to the same commit. Dry-run bypass is not a deployment.[^server-sync]
4. **[U/P]** Native rollback-by-history is blocked with automation enabled upstream and is not an exposed MCP tool here. Do not disable automation, perform history rollback, and restore it as a supposedly equivalent required plan. That also fails the requested persistent tag pin unless a separate source update is made.[^server-sync][^mcp-server][^local-billing]
5. **[D/U/I]** Completion requires the persistent tag, effective automation on, correct resolved operation revision, non-dry-run deployment evidence, live workload matching the old revision's desired content, and rollout/health appropriate to the bounded model. `status.sync.revision` identifies comparison context; `status.operationState.syncResult.revision` is also populated while operations are running, before success. Neither field alone proves deployment. Overall `Healthy` is derived from live resource health/customizations, not a health property of a Git commit.[^controller-sync][^health][^engine-health][^local-billing]

**[P/U/L/I] Explicit preservation objection:** the existing native update cannot retain the billing app labels/finalizer through the exposed schema, and the reference call does not. Do not solve this research finding by adding a grader exception implicitly. Options for the owner to choose are:

- Improve the connector's supported patch/round-trip preservation path and **repin/recapture the condition explicitly**, then require metadata preservation; or
- Keep this exact connector condition, disclose the narrowly bounded labels/finalizers loss as unavoidable wrapper collateral, and consciously decide whether that condition is acceptable; or
- Withhold qualification of this workflow under a no-collateral interpretation.

Never broaden that exception to source/policy/destination changes, unrelated Application metadata, or arbitrary label/finalizer edits. Do not claim extra unsupported fields are an available native repair tool.[^mcp-schema][^mcp-server][^server-update][^local-billing-data]

## 7. Payments: prune intention versus actual removal

**[D/U]** A sync without explicit revision resolves the app's configured `targetRevision`; in this fixture that is `main`, not an arbitrary “latest” commit across repositories. A one-off `revision` selects an operation's commit, but does not persistently edit `spec.source.targetRevision`. For payments with automation absent, omitted revision, explicit `main`, or the fixture's already-resolved current main SHA can all deploy the intended state, provided main identity is established and not changed. The moving-branch race is frozen by this fixture, not eliminated by the general API.[^server-sync][^tracking-doc][^local-payments-data]

**[P/U]** `prune:true` instructs deletion of extra tracked live resources missing from desired state. `dryRun:true` does not perform deletion. The engine can report `Pruned` with a dry-run message, or `PruneSkipped` when pruning is disabled or an object has `Prune=false`. A prune request can require confirmation; actual Kubernetes deletion can remain pending due to finalizers or propagation. The engine distinguishes pending deletions. Thus “sync requested with prune” and “ConfigMap is gone” are separate predicates.[^mcp-client][^sync-doc][^engine-sync]

**[L/I]** The two relevant legacy ConfigMaps are marked `requiresPruning:true`; neither has a projected resource prune override, finalizer, or deletion timestamp. That justifies straightforward bounded prune handling here. **Absence of a `targetManifest` field alone is not the pruning rule**: many retained fixture resources also omit it. Do not delete all resources without that field.[^local-payments-data][^local-resources][^local-model]

**[I] Completion and safety predicates:**

- A successful, non-dry-run production sync to the fixture's main SHA, with the production Deployment's live desired image/content updated and bounded rollout evidence if “running” is claimed; preserve application spec/policy/source/destination.[^local-payments][^local-payments-data][^server-sync][^engine-health]
- The legacy ConfigMap is absent by **cluster + group/kind + resource namespace/name**, not merely absent at its old UID-indexed storage key. Recreating the same named ConfigMap with another UID, orphaning it, removing it only from the Argo cache, or setting `deletionTimestamp` is not completed removal.[^local-payments][^local-payments-data][^kube-uid][^engine-sync]
- Retain the staging ConfigMap and other staging live resources at their initial state. Both Applications intentionally share resource namespace/name across different clusters; an application-name-only or namespace/name-only resource lookup must not collapse them.[^local-payments-data][^server-resource]
- Do not require an agent-issued HTTP DELETE: pruning is a downstream controller Kubernetes deletion caused by POST sync, not a DELETE to the Argo CD application API. Existing blanket DELETE-forbidden expectations should not be misapplied to internal controller effects. Conversely `delete_application` is not an acceptable way to remove one ConfigMap.[^local-payments][^mcp-client][^server-sync][^engine-sync]

**[D/U/P/I] Alternatives:** a whole-app sync with prune is the simplest native plan. A preliminary production sync without prune followed by a production sync with prune can also finish correctly, though less efficient. Direct resource deletion or selected-resource sync exists upstream but is not exposed by this pin; do not mandate, invent, or automatically bless an unavailable escape hatch. A nonmutating dry-run before a real sync is allowable, but a dry-run-only trajectory is incomplete.[^proto][^mcp-server][^local-payments]

## 8. History, status, health, and causal preservation

| Layer | What evidence establishes / what it does not |
| --- | --- |
| Application spec update | **[U]** Persists desired configuration, with update events/resource versions and possible source normalization. Does not itself establish a sync or rollout has completed.[^server-update] |
| Accepted sync | **[U]** Sets an Application operation and clears previous operation state; controller processes it separately. A concurrent-operation rejection is not evidence the first attempt failed.[^server-sync][^operation-helper] |
| Operation state | **[U]** Records phase, sync result/source/revision/resources, retries, and timestamps. A resolved revision is written before completion. Completed operations clear the top-level pending `operation`; later comparisons refresh sync/health status.[^controller-operation][^controller-sync] |
| Successful full sync history | **[U]** Successful, non-dry-run, non-resource-selected sync records deployment history, subject to `revisionHistoryLimit`. History IDs increment locally; actor may be automated or a user. Resource-selected sync and dry-run are not equivalent history producers. `ApplyOutOfSyncOnly=true` is not by itself a resource-selection list that suppresses history.[^controller-sync][^controller-history] |
| Live workload | **[U]** Desired manifests are applied; Kubernetes controller status and children evolve. Deployment health checks observed generation, updated/available replicas, pause, and failure conditions. A separate Git-record health flag cannot prove this layer.[^controller-sync][^kube-deployment][^engine-health] |
| Restart action | **[U]** Live patch plus action/resource events, not an Argo sync operation/history append. Kubernetes Deployment rollout revision and Argo Git deployment history are different histories.[^server-action][^controller-sync][^kube-deployment] |

**[L/I]** Protect independent configuration and unrelated resources, while allowing source-justified target-derived state: application/resource versions, sync/health comparisons, operation state, bounded history truncation/additions, events, and workload rollout descendants. Do not use whole-object equality for the target after a deployment, or blanket permission for all status/resource changes. The current local model's immediate completion, commit-derived health, status mutation of every app descendant, and unconditional successful operation response are shortcuts to audit, not vendor guarantees.[^local-model][^controller-operation][^controller-sync][^health]

## 9. Valid plans, retries, and lost responses

| Workflow | Valid native plan families; do not hard-code the reference sequence |
| --- | --- |
| Restart | Discover identity through app list/get and/or resource tree/manifests; optionally discover actions; run correctly scoped restart; optionally read worker/template/rollout state. Action-discovery GET is sensible but not a semantic prerequisite. No application sync/update, staging action, API restart, or pod delete workaround.[^mcp-server][^local-restart][^server-action] |
| Billing | Read current app, update supported fields with tag pin and automation retained, then observe controller completion. An additional same-target manual sync after the pin can be valid. No required explicit sync if the controller already achieved the result; no requirement that initiator be exclusively `automated:true` when a valid manual same-target operation completed.[^local-billing][^mcp-client][^controller-auto][^server-sync] |
| Payments | Namespaced production sync with prune, with optional discovery/dry-run/verification and recoverable extra same-target sync. Revision can be omitted, `main`, or its demonstrated current SHA. Keep staging and app spec unchanged.[^local-payments][^mcp-client][^server-sync] |

**[P] Transport repetition:** the pinned HTTP client has no explicit automatic request retry, idempotency key, or server-operation polling. Each mutation makes its own HTTP request; do not infer SDK retries or exactly-once execution from MCP request IDs.[^mcp-http][^mcp-client]

**[U/I] Lost restart response:** read the worker's live template/action evidence before retrying. Repeating restart in the same second can produce the same annotation and an empty merge diff, whereas retrying later can trigger another rollout. A timestamp delta is not guaranteed for every accepted duplicate call. Permit a justified duplicate target action after uncertain delivery; do not require multiple restarts or globally describe the action as idempotent.[^lua][^server-action]

**[U/I] Lost update response:** read the Application to determine whether the tag and policy persisted before resubmitting. A repeated same-spec update may still change metadata/resource version or emit events; the upstream update retries internal Kubernetes conflicts, which is different from caller replay. A full stale-spec replay can clobber unrelated concurrent changes. Do not insist on exactly one PUT or treat every second PUT as an unauthorized semantic change.[^server-update]

**[U/I] Lost sync response:** acceptance can precede response delivery; a second request may encounter an operation in progress. Once the first operation finishes, a repeated sync can start a new operation and append another history entry, potentially re-executing hooks. An already absent prune target is not grounds for fabricating an error or requiring another DELETE. Prefer read/observe-first recovery; exact history/event counts and call order are not success criteria.[^operation-helper][^controller-operation][^controller-history][^engine-sync]

**[D/U/I] Three retry layers must remain separate:** caller replay after network uncertainty; retries within one accepted operation using policy/backoff; controller auto-sync/self-heal scheduling and duplicate-attempt suppression. Docs' same-failed-revision auto-sync suppression does not remove configured retries within an operation. Baseline retry `refresh:true` can refresh source context on retry, but this fixture does not set it and the client schema cannot preserve/express it. Do not promise automatic eventual recovery from every transient failure or treat the reconciliation interval as a rollout deadline.[^auto-doc][^controller-operation][^controller-auto][^mcp-schema][^local-billing-data]

## 11. Benchmark-visible origin and credential configuration

**[L/P]** The current catalog sets `ARGOCD_BASE_URL="{world}"` and `ARGOCD_API_TOKEN` to a harness synthetic credential; the connector sends `Authorization: Bearer …`. Replay configuration supplies the corresponding synthetic authorization header. Do not place its value in task prose, research search terms, answers, or agent tool arguments. This service has empty `hosts` and no declared `runtime_origin_env`; the catalog's generic runtime-origin machinery therefore does not by itself produce an Argo public/account-origin binding. Destination Kubernetes URLs and source Git URLs are application data, **not the Argo CD API origin**.[^local-catalog][^local-origin][^mcp-http]

**[P]** In stdio, the connector reads its default outbound Argo origin/token from environment. HTTP/SSE transports can instead resolve session defaults from `x-argocd-base-url` / `x-argocd-api-token`; an optional `ARGOCD_TOKEN_REGISTRY_PATH` provides file-based origin/token mappings. All tools expose an optional **non-secret** `argocdBaseUrl`, but not a token argument. A default token is reused only for the normalized default origin; a different per-call origin requires a registry credential. Do not advise arbitrary override URLs as if the default token follows them. `MCP_READ_ONLY=true` unregisters mutation tools, so its effective setting belongs in condition admission.[^mcp-transport][^mcp-registry][^mcp-server]

**[P/I]** For HTTP transport, inbound MCP authentication (`MCP_AUTH_TOKEN`) is distinct from outbound Argo API authentication; catalog stdio is not that inbound network-listener case. Later origin/provenance work must record the effective launch origin, allowed override/registry policy, native package/surface pin, credential **source and class**, and observed request origin/identity without exposing token material. An internally rewritten world URL or replay header alone does not prove an agent selected the correct benchmark-visible origin or held real cloud credentials.[^mcp-security][^mcp-transport][^mcp-server][^local-catalog]

**[I] Bounded decision:** preserve default-origin use as a valid native plan; if public/account origin is needed for cross-arm fairness, provide a harness-controlled, non-secret connection descriptor and compatible origin/token binding. Do not require an unregistered per-call override, add a token to prompts, or quietly alter this connector pin while calling the condition unchanged.

## 12. Bounded implementation decisions and open qualifications

These are proposals for the parent task, **not edits made by this research sub-agent**.

1. **Use outcome + authorized causal request + preservation, not the reference call sequence.** Resolve exact app/resource identities including origin/cluster; retain forbidden application sync/edit for restart and frozen staging boundaries everywhere. Canonicalize calls before judging intent, and keep tool/API capability boundaries explicit.
2. **Make automation tri-state-aware.** Mirror the upstream effective-enabled predicate in modeled state and grading. Add `enabled:false` counterexamples when later validation is authorized; do not make an unsupported `enabled:true` tool field mandatory.
3. **Repair or withhold billing deployment qualification.** Provide a bounded, revision-scoped desired workload projection for the old release, apply it to live resources, and separate comparison, operation acceptance/completion, and rollout health. Until then, do not label status-only rollback as actual deployment. Do not arbitrarily assert the exact desired image tag solely from a Git tag; it should come from the modeled revision manifests.
4. **Adjudicate metadata reachability before preservation gates.** Choose explicit connector improvement/repinning, an openly scoped unavoidable-collateral exception, or nonqualification. No silent schema expansion, hidden preservation behavior absent upstream, blanket metadata exemption, or rewritten user instruction.
5. **Model the smallest honest asynchronous lifecycle.** Deterministic bounded transitions are acceptable as a stated replica abstraction; distinguish pending/running/succeeded/failed, dry-run, resource application/pruning, and live health. Immediate convergence may be a scheduling simplification, not permission to report unperformed effects. Preserve before/after evidence sufficient for lost-response recovery.
6. **Require relational prune completion.** The old UID's deletion is necessary here but not sufficient: assert absence by destination cluster/GK/namespace/name and protect the staging identity. Deletion timestamps/cache removal are not completed removal. Honor only needed prune protections or declare their absence; do not claim a complete Kubernetes garbage collector.
7. **Keep restart's guarantee bounded.** Live worker template patch and no unauthorized sync/edit are the minimal supported effect. If grading completed pod replacement, model only justified worker descendants and health progress; do not fabricate secret values or infer external 401 resolution.
8. **Treat wire/server compatibility as admission evidence.** Record a chosen Argo semantic baseline and legacy-action compatibility; preserve the exact connector's HTTP-error behavior in capture analysis. Exclude unsupported-success paths rather than rewarding permissive mock-only arguments. Per-call sync options can be omitted on the straightforward valid paths.
9. **Use retry-tolerant semantic evidence.** Allow read-first recovery, target-only repeated writes when justified by uncertain delivery, manual-same-target sync after billing pin, and controller-only completion. Do not require exact event/history counts or reward extra restart side effects. Track unrequested config changes across the whole trajectory, not only terminal state.
10. **Keep origin/credential assumptions explicit and sanitized.** Real MCP against a replica is not real cloud/cluster qualification; synthetic replay authentication is not native-account provenance. Any launch/origin change is a deliberate condition change outside this note.

**Remaining uncertainties:** no real vendor version is pinned by the local service; server/controller action customizations, real namespace enablement/RBAC, Kubernetes version, network error delivery, real tag immutability, real deletion/rollout timing, and installed dependency tree were not verified. The identified legacy adapter omission and operation `syncOptions` mismatch are source findings, not executed compatibility tests. The exact existing full-update schema's metadata limitation is demonstrated by source/fixture shape, but acceptability of that unavoidable collateral is a task-policy decision. None of these unknowns authorizes agents to reconfigure Argo, obtain credentials, change staging, or deploy unreviewed config.[^local-catalog][^actions-doc][^namespace-doc][^tracking-doc][^mcp-schema][^legacy-310][^proto]
